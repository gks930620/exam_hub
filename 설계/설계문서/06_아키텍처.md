## 1. 시스템 구성

> (구성도 그림은 만들어진 적이 없다. 현재 구조는 **단일 서버** — 컨테이너 하나가 React 화면과
> REST API 를 같이 서빙한다. 자세한 건 [진행사항/00_지금_상태.md](../../진행사항/00_지금_상태.md) §1.)

### 1-1. 데이터 파이프라인 (핵심 축)

```
공공데이터포털(큐넷 API)
   → ① 수집 배치 (@Scheduled 05:00, 임박 종목 17:00 추가)
   → ② diff·검증 (source_hash 비교, 날짜 무결성, 이상치 PENDING_REVIEW)
   → ③ PostgreSQL upsert + crawl_log
   → ④ notification_schedule 재계산 (이벤트별 발송 시각 파생)
   → ⑤ 발송 배치 (매 5분) → 관심 사용자 조회 → FCM → notification_log(멱등)
```

- 조회(API/pSEO)는 항상 DB만 바라봄 — **외부 API 실시간 호출 없음** → 수집 장애가 서비스 장애로 전파되지 않음
- 일정 변경 감지 시 SCHEDULE_CHANGED 알림 파생 (연기·취소 대응)

### 1-2. 웹 pSEO 서버 렌더

- `/cert/{slug}`, `/cert`, `/sitemap.xml`은 Spring 서버 렌더 HTML (Flutter Web 미사용 — SEO 원칙)
- 앱(Flutter)은 REST `/api/*`만 사용. 웹과 앱이 같은 서비스, 같은 DB
- 페이지 캐시 10분 (일 1회 수집이므로 사실상 정적)

### 1-3. 백엔드 패키지 구조 (공통 표준 준수)

```
src/main/java/com/examalert/
├── domain/          # Certificate, ExamSchedule, AppUser, UserFavorite,
│                    # NotificationSchedule, NotificationLog, CrawlLog + enum
├── repository/
├── service/         # CertificateService, FavoriteService, DdayService
├── collect/         # ScheduleSource(인터페이스), QnetScheduleSource, DiffService
├── scheduler/       # CollectScheduler, NotificationScheduler  ← noshow-guard 복사
├── notification/    # NotificationSender(FCM/LOG 구현)          ← noshow-guard 복사
├── web/             # /api 컨트롤러 + dto(record) · SeoPageController(/cert)
├── config/          # SecurityConfig, CORS, DataInitializer(!prod 데모)
└── common/          # ApiException, GlobalExceptionHandler, TimeUtil(KST)
```

### 1-4. Flutter 구조

```
lib/
├── config.dart      # API_BASE_URL (웹=origin, 에뮬레이터=10.0.2.2, --dart-define)
├── api/             # ApiClient(X-Device-Id 자동첨부) + models
├── state/           # FavoriteState, SettingsState (provider)
└── screens/         # home, search, certificate_detail, calendar, settings
```

패키지: `http`, `provider`, `shared_preferences`, `firebase_messaging` (최소 원칙)

## 2. 핵심 설계 결정

| 결정 | 선택 | 근거 |
|---|---|---|
| 계정 | 없음 — device_id(UUID) 헤더 | 가입 마찰 제거, 개인정보 최소화 (NFR-05) |
| 수집기 | `ScheduleSource` 인터페이스 | 공공 API 변경·소스 추가 대비 (리스크 1순위) |
| 알림 예약 | 일정에서 파생한 notification_schedule 테이블 | 발송 배치가 단순 조회로 동작, 변경 시 재계산 지점 하나 |
| 멱등성 | notification_log UNIQUE(user, schedule) | 배치 중복 실행에도 중복 푸시 0건 |
| 시간대 | TimeUtil(Asia/Seoul) + `ENV TZ=Asia/Seoul` | 접수 시각 오차 = 신뢰 붕괴 방지 |
| SEO | 검색 유입 페이지 전부 서버 HTML | Flutter Web SEO 불리 (기술 표준) |
