## 2. 데이터 수집 요구사항

| ID | 요구사항 | 상세 |
|---|---|---|
| DR-01 | 수집원 | 공공데이터포털 한국산업인력공단(큐넷) 국가기술자격 시험일정 API를 1차 소스로. 수집기는 `ScheduleSource` 인터페이스로 추상화해 소스 추가/교체 가능하게 |
| DR-02 | 수집 주기 | **일 1회 새벽 05:00 KST** (`@Scheduled` cron). 접수 시작 7일 이내 임박 종목은 **일 2회**(05:00/17:00) 재확인 |
| DR-03 | diff 감지 | 수집 결과를 기존 DB와 비교 → 신규/변경/삭제 판별. 변경 시 관심 사용자 변경 알림 트리거(FR-24) |
| DR-04 | 검증 규칙 | (a) 날짜 순서 무결성: 접수시작 ≤ 접수마감 < 시험일 < 발표일 (b) 기존 일정 대비 30일 이상 이동 시 자동 반영 보류 → `PENDING_REVIEW` 상태로 관리자 확인 (c) 필수 필드 누락 행은 스킵 + 로그 |
| DR-05 | 수집 로그 | 매 실행마다 crawl_log 기록: 소스, 시작/종료, 처리 건수(신규/변경/스킵), 성공 여부, 오류 메시지 |
| DR-06 | 장애 대응 | 2회 연속 실패 시 관리자 알림(LOG Sender→추후 이메일). 실패 중에도 기존 데이터로 서비스 지속, 웹에 "최종 수집 시각" 표기 |
| DR-07 | 원문 추적성 | 각 일정 행에 소스 식별자·원문 URL·수집 시각 저장 |

## 3. 비기능 요구사항

| ID | 항목 | 요구 수준 |
|---|---|---|
| NFR-01 | 시간대 | 모든 시간 판단은 `TimeUtil`(Asia/Seoul) 경유, Dockerfile `ENV TZ=Asia/Seoul` |
| NFR-02 | 성능 | pSEO 페이지 TTFB < 500ms (일정 데이터 DB 캐싱, 외부 API 실시간 호출 금지) |
| NFR-03 | 알림 정확성 | 예약 발송 시각 ±5분 이내. 중복 발송 0건 (멱등 키: user×schedule×이벤트유형) |
| NFR-04 | 가용성 | Railway 단일 서비스. 수집 실패가 조회/알림 기능을 중단시키지 않음 |
| NFR-05 | 개인정보 | 계정 없음. 기기 ID + FCM 토큰만 저장, 앱 삭제 감지(FCM 만료) 시 토큰 정리 배치 |
| NFR-06 | 에러 규약 | 응답 `{"message": "..."}` 통일 (공통 표준) |
| NFR-07 | 스택 | Spring Boot 3.5.x/Java 17/JPA + Flutter(provider) + PostgreSQL(운영)/H2(개발) + FCM + Railway |
| NFR-08 | 코드 재사용 | noshow-guard의 scheduler/notification 패키지 복사 후 시작 |
| NFR-09 | 법적 고지 | 모든 일정 화면에 "참고용 정보, 최종 확인은 시행기관(큐넷)" 문구 |

## 4. v2 제외 항목 (명시적 아웃 오브 스코프)

| 항목 | 제외 사유 |
|---|---|
| 합격 발표 알림·합격 조회 | 발표 데이터 소스 별도 확보 필요, MVP 가치(접수 알림) 흐림 |
| 커뮤니티(스터디·후기) | 운영 부담 최대 요인. 저유지보수 원칙 위배 |
| 문제풀이·학습 콘텐츠 | 별도 제품 영역. "일정 비서" 포지셔닝 훼손 |
| 국가전문자격·민간자격 확장 | 소스 다변화는 국가기술자격 안정화 후 |
| 계정/로그인·기기 간 동기화 | 기기 ID로 충분. 프로 결제 도입 시점에 재검토 |
| 초성 검색·자동완성 고도화 | 부분 일치로 MVP 충분 |
| 알림톡·이메일 채널 | Sender 인터페이스만 유지, 채널 추가는 수요 확인 후 |
