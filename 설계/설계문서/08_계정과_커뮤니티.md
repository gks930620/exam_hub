# 08. 계정(소셜 로그인) · 커뮤니티 설계

> 작성 2026-08-06. **사용자 결정으로 방향이 바뀌었다** — 기존 "계정 없음 · 기기식별(X-Device-Id)"을 폐기하고
> 소셜 로그인 기반 계정제로 간다. 01~06 문서의 "인증 = 기기식별" 서술은 이 문서로 대체된다.
>
> 확정된 것(2026-08-06 사용자 결정):
> 1. **로그인은 소셜 단독** — 카카오·구글 OAuth2. 자체 이메일/비밀번호 계정은 만들지 않는다.
>    (2026-08-10 추가: **매니저만 예외** — §4-1-1)
> 2. **기기식별(X-Device-Id)은 완전 제거** — `AppUser.deviceId` 폐기, 기존 데이터 이관 없음.
> 3. **커뮤니티는 게시판 + 댓글** — 추천·신고는 이번 범위 밖.

---

## 1. 무엇이 로그인 없이 되고, 무엇이 로그인이 필요한가

제품의 성격상 **시험 정보 자체는 최대한 열어 두고**, 개인화된 것만 잠근다.

| 기능 | 비로그인 | 로그인 |
|---|:-:|:-:|
| 시험 검색 / 목록 / 상세 / 연간 일정 | ✅ | ✅ |
| 커뮤니티 글·댓글 **읽기** | ✅ | ✅ |
| **내 시험(관심) 등록·조회** | ❌ | ✅ |
| **알림 설정** | ❌ | ✅ |
| **캘린더(내 시험 기준)** | ❌ | ✅ |
| 커뮤니티 글·댓글 **쓰기/수정/삭제** | ❌ | ✅ |

> 비로그인 사용자가 잠긴 기능을 호출하면 **401 `UNAUTHENTICATED`** 를 주고, 프런트는 로그인 유도 화면을 띄운다.
> 지금처럼 헤더 누락 400 이 아니다 — 400 은 "요청이 잘못됨", 401 은 "로그인이 필요함"으로 의미가 다르다.

## 2. 데이터 설계 (ERD 변경)

### 2-1. 폐기 / 신설

| 대상 | 변경 |
|---|---|
| `app_user.device_id` | **삭제** — 대신 `provider` + `provider_id` |
| `AppUser` | → **`Member`** 로 개명(계정 개념이 되었으므로). 알림 토글 3종은 그대로 이관 |
| `user_favorite.app_user_id` | → `member_id` |
| `notification_log.app_user_id` | → `member_id` |
| `Plan`(FREE/PRO) | **유지하되 사용 안 함** — 유료화 제거 방향(01 §1-1)에 따라 관심 3개 제한은 해제. 컬럼은 남겨 두고 서비스에서 제한 로직만 제거 |
| `board`, `post`, `comment` | **신설** |

### 2-2. member

```
member
  id              BIGINT PK AUTO_INCREMENT
  provider        VARCHAR(10)  NOT NULL   -- KAKAO | GOOGLE | LOCAL(매니저 전용)
  provider_id     VARCHAR(64)  NOT NULL   -- 공급자가 주는 고유 id (sub)
  email           VARCHAR(255) NULL       -- 카카오는 미동의 시 없음 → NULL 허용
  nickname        VARCHAR(30)  NOT NULL   -- 커뮤니티 표시명. 최초 공급자 값 → 이후 수정 가능
  profile_image   VARCHAR(500) NULL
  password_hash   VARCHAR(100) NULL       -- 매니저(LOCAL)만. 소셜은 항상 NULL
  role            VARCHAR(10)  NOT NULL   -- USER | ADMIN
  status          VARCHAR(10)  NOT NULL   -- ACTIVE | WITHDRAWN
  notify_reg      BOOLEAN NOT NULL DEFAULT TRUE
  notify_exam     BOOLEAN NOT NULL DEFAULT TRUE
  notify_change   BOOLEAN NOT NULL DEFAULT TRUE
  created_at      DATETIME NOT NULL
  updated_at      DATETIME NOT NULL
  UNIQUE uk_member_provider (provider, provider_id)
  UNIQUE uk_member_nickname (nickname)
```

- **식별 키는 `(provider, provider_id)`** 다. 이메일이 아니다 — 카카오는 이메일 제공 동의가 선택이라 없을 수 있고, 같은 사람이 카카오/구글로 각각 가입하면 **별개 계정**이 된다(계정 통합은 이번 범위 밖).
- `nickname` 중복 시 뒤에 숫자를 붙여 자동 회피(`홍길동`, `홍길동2`).

### 2-3. 커뮤니티

```
board                      -- 고정 목록. 코드로 초기 적재
  id        BIGINT PK
  code      VARCHAR(20) NOT NULL UNIQUE   -- FREE | QNA | REVIEW
  name      VARCHAR(30) NOT NULL          -- 자유게시판 | 질문게시판 | 시험후기
  sort_order INT NOT NULL

post
  id          BIGINT PK AUTO_INCREMENT
  board_id    BIGINT NOT NULL FK → board
  member_id   BIGINT NOT NULL FK → member
  title       VARCHAR(200) NOT NULL
  content     TEXT NOT NULL
  view_count  INT NOT NULL DEFAULT 0
  comment_count INT NOT NULL DEFAULT 0   -- 목록 N+1 방지용 비정규화
  deleted     BOOLEAN NOT NULL DEFAULT FALSE
  created_at  DATETIME NOT NULL
  updated_at  DATETIME NOT NULL
  INDEX idx_post_board_created (board_id, created_at DESC)

comment
  id         BIGINT PK AUTO_INCREMENT
  post_id    BIGINT NOT NULL FK → post
  member_id  BIGINT NOT NULL FK → member
  content    VARCHAR(1000) NOT NULL
  deleted    BOOLEAN NOT NULL DEFAULT FALSE
  created_at DATETIME NOT NULL
  updated_at DATETIME NOT NULL
  INDEX idx_comment_post (post_id, created_at ASC)
```

- **삭제는 soft delete**(`deleted`). 댓글이 달린 글을 물리 삭제하면 대화가 사라진다. 목록/상세에서 제외하고, 삭제된 글의 댓글도 함께 감춘다.
- `comment_count` 는 댓글 생성/삭제 시 갱신. 목록에서 매번 count 쿼리를 돌리지 않기 위한 것.
- 대댓글(계층)은 **이번 범위 밖** — 필요해지면 `parent_id` 추가.

## 3. 인증 방식 — 세션이 아니라 JWT

프런트가 **별도 도메인에 배포**되는 CSR 이라(01_AI_작업큐 §3) 쿠키 세션은 SameSite·CORS 처리가 번거롭다.
→ **OAuth2 로그인 성공 시 서버가 JWT 를 발급**하고, 프런트가 `Authorization: Bearer` 로 보낸다.

### 3-1. 흐름

```
① 프런트: window.location = {API}/oauth2/authorization/kakao
② 카카오 로그인·동의 → 서버 /login/oauth2/code/kakao 로 콜백
③ 서버: provider_id 로 member 조회, 없으면 생성(최초 로그인 = 회원가입)
④ 서버: JWT(access) 발급 → 프런트 콜백 URL 로 리다이렉트
      {FRONT}/oauth/callback#token=eyJ...
⑤ 프런트: 토큰을 localStorage 에 저장, 이후 모든 요청에 Authorization 헤더
```

- **토큰을 쿼리스트링(`?token=`)이 아니라 프래그먼트(`#token=`)로 넘긴다.** 쿼리는 서버 접근로그·Referer 에 남는다.
- access 토큰 만료 24시간. **refresh 토큰은 이번 범위 밖** — 만료되면 다시 로그인. (운영 붙일 때 재검토)
- 서명 키는 `JWT_SECRET_KEY` env. 미설정 시 운영에서 fail-fast(`RailwayDeploymentValidator` 에 추가).

### 3-2. 서버 구성

| 요소 | 역할 |
|---|---|
| `SecurityConfig` | `/api/certificates/**`·`/api/community/**` GET 은 permitAll, `/api/me/**`·쓰기 요청은 authenticated |
| `OAuth2SuccessHandler` | ③④ 담당. member upsert + JWT 발급 + 프런트로 리다이렉트 |
| `JwtAuthenticationFilter` | `Authorization: Bearer` 파싱 → SecurityContext 에 `MemberPrincipal` 적재 |
| `@CurrentMember` | 컨트롤러 파라미터 리졸버. 기존 `@CurrentDevice` 를 대체 |

> `@CurrentDevice`·`DeviceIdArgumentResolver`·`AppUserService.getOrCreate(deviceId)` 는 **삭제**된다.

## 4. API 계약

### 4-1. 인증

| 메서드 | 경로 | 인증 | 설명 |
|---|---|:-:|---|
| GET | `/oauth2/authorization/{kakao\|google}` | — | 로그인 시작(스프링 시큐리티 기본 경로) |
| GET | `/api/me` | 필요 | 내 정보 `{id, nickname, email, profileImage, phoneNumber, provider, role}` |
| PATCH | `/api/me` | 필요 | 닉네임 변경 `{nickname}` |
| PUT | `/api/me/email` | 필요 | **알림 받을 이메일 직접 입력** `{email}` — 아래 참고 |
| PUT | `/api/me/phone` | 필요 | 휴대폰번호 입력 `{phoneNumber}`(숫자만 저장). 알림톡용 — **지금은 발송에 쓰지 않는다** |
| DELETE | `/api/me` | 필요 | 회원 탈퇴(status=WITHDRAWN, 글·댓글은 남기고 작성자 표기만 "탈퇴한 사용자") |

> **왜 이메일을 직접 받나** — 소셜에서 못 받기 때문이다.
> 카카오의 `account_email` 동의항목은 **비즈 앱(사업자 정보 등록) 전환 후에만** 켤 수 있고,
> 켜지 않은 채 scope 에 넣으면 **KOE205 로 로그인 자체가 막힌다**(실제로 겪음 → `oauth.yml` 에서 뺐다).
> 알림 채널이 이메일뿐인 지금, 직접 입력이 **유일한 수신 경로**다.
>
> - 형식이 틀리면 **400**(`@Email`), 빈 값은 400 이 아니라 **null 저장 = 수신 해제**다.
> - 이메일이 없으면 내 정보 화면이 "알림을 받을 수 없는 상태"라고 경고한다 — 조용히 안 가는 게 최악이라서.

### 4-1-1. 매니저(운영자) — 폼 로그인 예외 (2026-08-10 결정)

| 메서드 | 경로 | 인증 | 설명 |
|---|---|:-:|---|
| POST | `/api/manager/login` | — | 아이디/비밀번호 → JWT(ADMIN). 실패는 사유를 구분하지 않고 **401** |
| GET | `/api/manager/available` | — | 매니저 계정이 설정돼 있는지(로그인 화면 안내용). 아이디는 주지 않는다 |
| * | `/api/admin/**` | **ADMIN** | 운영 기능. 로그인만 한 일반 회원은 **403** |
| GET | `/api/admin/data-map` | **ADMIN** | 자동/수기 구분 + 원본 사이트 링크 + 적재 현황 |

**왜 소셜 단독 원칙을 깨나** — 운영 계정이 카카오·구글에 묶이면 그쪽이 막히는 날 운영 자체가
멈춘다. 인수인계도 개인 SNS 계정을 넘기는 꼴이 된다. 그래서 매니저만 자체 계정을 쓴다.

**어떻게 안전하게 유지하나**

- `AuthProvider.LOCAL` + `Member.passwordHash`(BCrypt). **소셜 계정은 해시가 항상 null** 이라
  `canLoginWithPassword()` 가 false → 소셜 사용자가 매니저 창을 통과할 수 없다.
- **가입 경로가 없다.** `MANAGER_USERNAME`/`MANAGER_PASSWORD` 환경변수로만 생성·갱신된다
  (`ManagerAccountInitializer`). 가입을 열면 그 자체가 공격면이고, 누가 매니저인지를
  코드가 아니라 사람이 관리하게 된다.
- 비밀번호 10자 미만이면 계정을 만들지 않는다(로그만 남기고 **기동은 계속** — 매니저 하나 때문에
  서비스 전체가 안 뜨면 손해가 더 크다).
- 발급 토큰은 소셜과 **같은 JWT** — 인증 방식만 다르고 그 뒤는 동일하다.
- 비밀번호 재설정 기능은 없다. 계정이 하나뿐이라 보낼 곳이 없다 —
  환경변수를 바꾸고 재기동하면 갱신되는 것이 유일한 복구 경로다.

### 4-2. 기존 API 변경

| 경로 | 변경 |
|---|---|
| `GET/POST/DELETE /api/me/favorites` | X-Device-Id → **JWT 필수**. 헤더 누락 시 400 → **401** |
| `GET/PUT /api/me/notify-settings` | 동일 |
| `GET /api/me/calendar` | 동일 |
| `GET /api/certificates/**` | 변경 없음(비로그인 허용). 단 `favorited` 는 **로그인 시에만** 채워지고 비로그인은 항상 false |

### 4-3. 커뮤니티

| 메서드 | 경로 | 인증 | 설명 |
|---|---|:-:|---|
| GET | `/api/community/boards` | — | 게시판 목록 |
| GET | `/api/community/posts?board=FREE&page=0&size=20` | — | 글 목록(페이징, 최신순) |
| GET | `/api/community/posts/{id}` | — | 글 상세(+조회수 1 증가) |
| POST | `/api/community/posts` | 필요 | 작성 `{boardCode, title, content}` |
| PUT | `/api/community/posts/{id}` | 필요·본인 | 수정 |
| DELETE | `/api/community/posts/{id}` | 필요·본인 | soft delete |
| GET | `/api/community/posts/{id}/comments` | — | 댓글 목록 |
| POST | `/api/community/posts/{id}/comments` | 필요 | 댓글 작성 `{content}` |
| DELETE | `/api/community/comments/{id}` | 필요·본인 | soft delete |

**에러 규약** (기존 `ErrorResponse` 형식 그대로)

| 상황 | 코드 |
|---|---|
| 비로그인으로 보호 API 호출 | 401 `UNAUTHENTICATED` |
| 남의 글 수정·삭제 | 403 `ACCESS_DENIED` |
| 없는 글/댓글 | 404 `NOT_FOUND` |
| 제목·내용 길이 위반 | 400 `VALIDATION_ERROR` |

## 5. 화면 (프런트)

| 화면 | 경로 | 비고 |
|---|---|---|
| 로그인 | `/login` | 카카오·구글 버튼 2개. 잠긴 기능 접근 시 여기로 |
| OAuth 콜백 | `/oauth/callback` | 프래그먼트에서 토큰 회수 → 저장 → 원래 가려던 곳으로 |
| 게시판 목록 | `/community` | 게시판 탭 + 글 목록 |
| 글 상세 | `/community/posts/:id` | 본문 + 댓글 |
| 글 쓰기/수정 | `/community/write`, `/community/posts/:id/edit` | 로그인 필요 |
| 내 정보 | `/me` | 닉네임 변경·탈퇴 |

- 헤더 우측에 **로그인 상태**(프로필 이미지·닉네임 / 로그인 버튼)를 둔다.
- 사이드바에 **커뮤니티** 항목 추가.
- 보호 라우트는 `<RequireAuth>` 로 감싸 비로그인 시 `/login` 으로 보낸다.

## 6. 사람이 해야 할 것 (막힘 지점)

소셜 로그인 단독이라 **키가 없으면 로컬에서도 로그인이 안 된다.**

| # | 할 일 | 어디서 | 결과로 얻는 값 |
|:-:|---|---|---|
| 1 | 카카오 개발자 앱 생성 + 카카오 로그인 활성화 + Redirect URI 등록 | developers.kakao.com | `KAKAO_CLIENT_ID`(REST API 키), `KAKAO_CLIENT_SECRET` |
| 2 | 구글 클라우드 OAuth 클라이언트(웹) 생성 + 승인된 리디렉션 URI 등록 | console.cloud.google.com | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
| 3 | JWT 서명 키 아무 긴 랜덤 문자열 생성 | — | `JWT_SECRET_KEY` (32자 이상) |

**등록할 Redirect URI** (로컬 기준)
```
http://localhost:8081/login/oauth2/code/kakao
http://localhost:8081/login/oauth2/code/google
```

> 키가 오기 전까지: 로그인 외 기능(시험 조회·커뮤니티 읽기)은 개발·검증 가능하다.
> 로그인이 필요한 부분은 테스트에서 JWT 를 직접 발급해 검증한다(실제 카카오 호출 없이).

## 7. 작업 순서

1. **(senior-dev)** 계약 기반 테스트 선작성 — 인증 401/403, 커뮤니티 CRUD, 권한
2. **(backend-dev)** `Member` 전환(+`AppUser` 제거) → 시큐리티/JWT → 커뮤니티 도메인·API
3. **(frontend-dev)** 로그인·콜백·인증 상태 → 보호 라우트 → 커뮤니티 화면
4. **(사람)** 키 3종 주입 → 실제 소셜 로그인 리허설
5. **(qa)** 비로그인/로그인/타인 글 시나리오 검증

> ⚠️ 2단계는 **기존 데이터와 호환되지 않는다**(device_id 제거). 로컬은 매 기동 재생성이라 무관하고,
> 운영은 아직 미배포라 마이그레이션 대상이 없다 — 지금이 바꾸기 가장 싼 시점이다.
